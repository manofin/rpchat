## 0. 이 문서가 존재하는 이유

`clock_minutes`는 F9 설계에서 **server 정본**으로 계약됐지만, 라이브에서 한 번도 저절로 움직인 적이
없다. 원인은 allow-list가 아니라 두 가지다 — 서버가 「검증·저장」만 구현하고 「진행」을 구현하지
않았다는 것, 그리고 델타 판정기의 질문 형태가 시간을 상태 변화로 보지 않게 만든다는 것.

그런데 시간을 그냥 켜면 안 되는 이유가 하나 더 있다. **델타는 생성 *전에* `conversations.scene_json`
에 저장되고, 중단·실패 시 되돌아가지 않는다.** 지금은 시계가 멈춰 있어 이 잔존이 눈에 띄지 않지만,
`advance_minutes`를 켜는 순간 「중단할 때마다 시간이 흐른다」가 된다.

그래서 이 ADR은 시간 정책과 **scene 커밋 시점**을 함께 결정한다. 후자가 먼저 닫히지 않으면 전자를
열 수 없다.

## 1. 확인된 사실 (읽기 전용 실측)

### 1.1 계약과 구현의 차이

| | 계약 | 구현 |
|---|---|---|
| `clock_minutes` | ADR-F9 소유권 표: 정본 `server`, 모델은 `advance_minutes` 제안만.<br>`0010_scene_state.sql`: *"server SoT; model proposes advance_minutes at F9E"* | `APPLY_KEYS`에 `advance_minutes` 존재, `applySceneDelta.ts:317`이 증분 적용. **서버가 스스로 진행시키는 코드는 없다** |
| `day_index` | 소유권 표에 **행 자체가 없다** | `initScene.ts:88` 최초 1회 쓰기뿐. `APPLY_KEYS`·델타 프롬프트·증가 코드 전부 없음 |

ADR-F9 §매트릭스는 *"여기 없는 필드는 기본 거부다"*라고 못박았으므로, `day_index`는 현재 **계약상
아무도 못 바꾸는 필드**다. 이건 의도된 동결이 아니라 표에서 빠진 결과로 보인다.

### 1.2 델타 판정기가 시간을 놓치는 방식

`sceneDeltaPrompt.ts:75`의 과업 정의:

> 너는 장면 진행 판정기다. … 사용자 입력으로 장면 상태가 **실제로 바뀌었는지만** 판정한다.
> 바뀐 것이 없으면 `base_version` 만 담은 객체를 낸다.

`advance_minutes`는 허용값 목록(`:92`)과 출력 예시(`:108`)에 둘 다 있다. 그런데 시간은 사용자 입력이
*바꾸는* 것이 아니라 *흐르는* 것이라, 「입력이 상태를 바꿨나」를 묻는 판정기는 평범한 대화에서 늘
「아니오」를 답한다.

**결정적 관측** — 2026-09-02, 대화 `552e0205…`:

```
사용자 입력: "측정 끝났어요. 시간도 30분쯤 지났고, 밖이 개어서 날씨가 맑아졌네요."
결과       : weather → clear  (적용됨)
             clock_minutes    (미적용, 545 유지)
```

**같은 한 문장에서 `weather`는 적용되고 `advance_minutes`는 적용되지 않았다.** 사용자가 숫자까지
명시했는데도 그렇다. 이건 모델이 시간을 몰라서가 아니라, 판정기 프레이밍에서 날씨는 「바뀐 상태」로,
시간은 「바뀐 상태가 아님」으로 읽히기 때문이라는 가설을 강하게 지지한다.

### 1.3 생성 전 쓰기의 실제 reader 목록 (요청 항목)

`chat.ts`의 세 경로가 생성 **전에** `conversations.scene_json`을 쓴다(`:432`, `:805`, `:1074`).
주석은 *"the passes and any concurrent reader see the same world"*라고 하지만, 실측하면 다르다.

`conversations.scene_json`을 읽는 모든 경로:

| 위치 | 무엇 | 이 쓰기의 소비자인가 |
|---|---|---|
| `chat.ts:209` | `scene.format` 분기 | **아니다** — 생성 전 쓰기보다 앞 |
| `chat.ts:348 / 738 / 1008` | `resolveSceneBase`의 `conversationScene` 인자 | **아니다** — 같은 턴에서는 쓰기보다 앞. 다만 *다음* 턴의 폴백으로는 소비된다 |
| `routes/conversations.ts:131` | `convOut()` — GET/목록 응답의 `scene` | **그렇다** (유일한 실시간 소비자) |
| `routes/conversations.ts:283` | PATCH 병합 | 사용자 편집 경로. 생성 중 발생 가정 없음 |
| `prompt/builder.ts:177` | **1:1 경로**의 `renderScene` | 아니다 — 1:1은 델타를 적용하지 않는다 |

그리고 생성 전 쓰기와 finish 쓰기 **사이에 `scene_json`을 다시 읽는 코드는 없다.** 패스들은 전부
in-memory 값을 받는다(`renderPassN({… scene …})`, `passFWith(planInput, …)`,
`planPassE(planInput, …)`, `finishBeat(planInput, …)`, `passCWith(planInput, finished)`).

> **결론: 생성 전 쓰기는 모델 파이프라인의 필수 조건이 아니다.** 실시간 소비자는
> `GET /api/conversations`를 치는 클라이언트 하나뿐이고, 나머지 영향은 *다음* 턴의 레거시 폴백이다.

### 1.4 클라이언트가 그 값으로 실제 무엇을 그리는가

`useChat.ts:46`이 **생성 중 700ms 주기로 대화를 재조회**하므로 동시 reader는 가설이 아니라 실재한다.
다만 `conv.scene`의 소비처는 둘뿐이다:

- `ChatPage.tsx:170, 191` — `conv.scene.format`. 턴 중에 바뀌지 않는다.
- `ChatPage.tsx:678` — 바텀시트의 `sceneLine`. **`typeof v === 'string'` 필터가 걸려 있어
  `clock_minutes`(number)는 애초에 표시되지 않는다.** 시트를 열어놔야 보인다.

**대화 화면에 보이는 시각(`1일차 · 09:38 · cloudy · bureau_lobby`)은 `conv.scene`이 아니라
`renderBeat`가 만들어 메시지 행에 저장한 헤더 블록에서 온다.** 그 헤더는 in-memory `plan.applied.state`
로 만들어지므로 커밋 시점을 바꿔도 헤더 내용은 그대로다.

### 1.5 중단 턴 잔존은 스냅샷 슬라이스로 닫히지 않았다

`scene-branch-snapshot` 이후에도 경로가 남아 있다(코드 경로 추론, 실행 관측 아님):

```
턴 N    델타 +10 → conversations.scene_json = 588  (생성 전 쓰기)
        Pass N 실패/중단 → catch → stamp 없음
        header 블록은 남음 (beat_seq 0, scene_state 없음)
턴 N+1  조상 탐색이 턴 N의 시작 블록에서 멈춤 (첫 턴 시작에서 멈추는 규칙)
        스냅샷 없음 → conversations.scene_json 폴백 = 588
```

즉 「첫 스냅샷이 아니라 첫 턴 시작에서 멈춘다」는 규칙이 안전한 선택인 동시에, **중단 턴의 잔존을
건너뛰지 않고 물려받게 만든다.**

### 1.6 원자성 현황

- `apps/server/src/`에서 `db.transaction`은 **마이그레이션 러너(`db/index.ts:30`) 한 곳뿐**이다.
  생성 경로에 트랜잭션이 없다.
- 한 턴의 최종 커밋은 최소 3개의 독립 SQL이다: 블록 행 INSERT/UPDATE → `conversations.scene_json`
  UPDATE(`:628`) → `scene_state` stamp UPDATE(`:630`) → `generation_log` INSERT.
- 프로세스가 중간에 죽으면 `interruptOrphanStreaming`이 **`status='streaming'` 행만** 접는다.
  비트 블록은 `addBlock`이 `'complete'`로 넣으므로 접히지 않는다. 스트리밍 focus 행 하나만 대상이다.

## 2. 정책 S1 vs S2

### S1 — 선행 적용 세계 (현행)

```
커밋된 scene V → delta 계산 → conversations.scene_json = V' 저장 → 패스 → 완료 또는 중단
```

- 생성 중 세계도 정본으로 노출
- 중단 턴 상태 잔존 (§1.5)
- 다음 턴의 레거시 폴백이 그 상태를 계승
- 동시 reader가 미완료 턴 상태를 볼 수 있음

### S2 — 완료된 턴의 세계 (제안)

```
커밋된 scene V → delta 계산 → 패스는 in-memory 결과 사용 → 성공 → scene_json 과 after_delta 동시 확정
```

- 성공한 턴만 정본을 바꾼다
- 중단·실패 시 정본 불변
- 동시 reader는 완료 전까지 이전 확정 상태를 본다
- 스냅샷과 conversation scene의 커밋 시점이 일치한다

### 요청하신 다섯 가지 확인 결과

| 확인 | 결과 |
|---|---|
| 생성 중 `scene_json`을 읽는 서버 내부 경로가 정말 없는가 | **없다** (§1.3). 두 쓰기 사이에 읽기 0 |
| SSE나 클라이언트가 생성 도중 새 scene을 요구하는 계약이 있는가 | SSE 이벤트에 scene은 **실리지 않는다**. 클라이언트는 700ms 폴링으로 대화를 재조회하지만, `conv.scene` 소비처는 `format`(불변)과 바텀시트 문자열 필드뿐이고 `clock_minutes`는 number라 표시되지 않는다 (§1.4) |
| 최종 저장 실패 시 메시지와 scene의 원자성 | **보장 없음.** 트랜잭션 미사용, 3~4개 독립 SQL (§1.6). 이건 S1/S2와 무관한 기존 위험이며 §7에서 별도로 다룬다 |
| dialog·hunter도 beat와 동일하게 S2 전환 가능한가 | **가능하다.** 세 경로가 같은 형태다 — 각자 `scene` 읽기 → `planX` → 생성 전 쓰기 → finish 쓰기 → stamp. 생성 전 쓰기 3줄(`:432`, `:805`, `:1074`)이 구조적으로 동일하다 |
| 생성 중 프로세스가 죽었을 때 부분 메시지와 scene의 관계 | S1: 블록은 `complete`로 남고 scene은 이미 전진, 스냅샷 없음. S2: 블록은 `complete`로 남고 **scene은 불변**, 스냅샷 없음. S2가 엄격히 낫다 |

### 결정: **S2 채택**

```
conversations.scene_json = 마지막으로 성공 완료된 턴의 커밋된 scene
```

후속 구현이 지켜야 할 계약:

```
생성 시작:
  커밋된 scene에서 기준 상태 해결
  conversations.scene_json 은 변경하지 않는다
생성 중:
  delta 와 후속 패스는 in-memory scene 을 쓴다
생성 성공:
  완성된 scene 을 snapshot after_delta 와 conversations.scene_json 에 함께 반영
생성 실패·중단:
  conversations.scene_json 불변
  완료 snapshot 없음
```

근거는 §1.3 하나로 충분하다 — 생성 전 쓰기는 패스가 소비하지 않으므로, 옮겨도 모델 파이프라인이
바뀌지 않는다. 남는 대가는 「생성 중 동시 reader가 이전 확정 상태를 본다」인데, §1.4에 따르면
사용자에게 보이는 변화가 사실상 없다. **생성 중 바텀시트가 이전 확정 상태를 잠시 보여주는 것은,
미완료 상태를 선반영하는 것보다 올바른 동작으로 판정한다.**

구현은 `scene-commit-on-success` 슬라이스로 분리한다(§8). 이 결정은 §7의 원자성 위험을 해소하지
않는다 — 그 항목은 별도로 남는다.

### S2 전환 시 관찰 가능한 제품 변화 (요청 항목)

| 변화 | 관찰 가능성 |
|---|---|
| 비트 헤더의 시각·날씨·장소 | **변화 없음** — in-memory `plan.applied.state`로 렌더돼 메시지에 저장됨 |
| 대화 화면 본문 | 변화 없음 |
| 대화 설정 바텀시트의 `sceneLine` | 생성이 끝날 때까지 이전 값 표시. 시트를 열어둔 채 생성해야 보이고, 문자열 필드에 한정 |
| `GET /api/conversations/:id` 의 `scene` | 생성 중 이전 확정 상태 반환 (현재는 델타 적용 상태) |
| 중단·실패한 턴 이후의 세계 | **바뀐다** — 지금은 델타가 남고, S2에서는 남지 않음. 이게 이 전환의 목적 |
| 성공한 턴의 최종 상태 | 변화 없음 |

## 3. `day_index` 소유권 (채택)

아래 행을 ADR-F9 §매트릭스에 추가한다. **이 ADR은 F9 파일을 수정하지 않는다** — 표 반영은 별도
`PRD`/`ADR` 잠금으로 한다. F9는 accepted 상태로 무수정 유지한다(F5→F8 선례).

| 필드 | 정본 소유자 | 모델이 낼 수 있는 것 | 서버 검증 | 실패 시 |
|---|---|---|---|---|
| `scene.day_index` | **server** | **없음 (직접 제안 불가)** | `clock_minutes` 롤오버에서만 서버가 증가. 최소값 `1` | 기존 유효값 유지 |

```
field            : scene.day_index
canonical owner  : server
model output     : 직접 제안 불가
minimum          : 1
null fallback    : 1
update trigger   : clock_minutes rollover only
failure behavior : 기존 유효값 유지
```

모델은 `advance_minutes`만 제안할 수 있고 `day_index`를 직접 설정할 수 없다.

### 3.1 clock 정규화 계약 (채택)

`clock_minutes`는 **하루 안의 정규화된 분 값**이다.

```
유효 범위 : 0..1439

적용:
  total          = clock_minutes + advance_minutes
  day_index     += floor(total / 1440)
  clock_minutes  = total % 1440
```

따라서:

```
clock 578 + advance 1440
  → clock 578
  → day_index +1
```

| 항목 | 결정 |
|---|---|
| 저장 형태 | `0..1439` 정규화. 세 렌더러가 이미 `% 1440`로 감으므로(`renderBeat:108`, `renderHunter:169`, `renderDialog:66`) 저장값과 표시값이 갈라지지 않는다 |
| `ADVANCE_MINUTES_MAX` | **1440 유지** (초안의 하향 제안은 채택하지 않는다) |
| 다일 진행 | 한 delta당 최대 하루. 다일 진행 제안은 허용하지 않는다 |
| 역방향 시간 | 지원하지 않는다. `applySceneDelta:316`의 `v >= 0` 유지 |
| 기존 `day_index = NULL` 행 | **읽을 때 `1`로 해석**하고, 다음 성공 완료 상태를 저장할 때 정규화한다. **백필·마이그레이션 없음** |

`initScene.ts:65`가 이미 `1`을 기본값으로 쓰므로 최소값 `1`은 기존 라이브 행과 어긋나지 않는다.

## 4. 성공·실패·중단·regenerate 매트릭스

S2를 전제로 한 제안. **모든 시간 반영은 성공 완료 시점에만 일어난다.**

| 상황 | 델타 전체 | 시간 (`advance_minutes`) | `day_index` | scene 커밋 | 스냅샷 |
|---|---|---|---|---|---|
| 성공 완료 (모델 유효값) | 검증분 적용 | **모델 값** | 롤오버 시 서버 증가 | O | O |
| 유효 delta인데 `advance_minutes` **누락** | 나머지 키 적용 | **서버 기본값** | 위와 같음 | O | O |
| 명시적 `advance_minutes: 0` | 나머지 키 적용 | **시간 불변** (기본값으로 덮지 않음) | 불변 | O | O |
| `advance_minutes` 값 오류 (타입/범위) | 기존 검증 계약대로 해당 키만 무시 | **불변** (기본 시간 적용 안 함) | 불변 | O | O |
| 델타 파싱 실패 (`parseSceneDelta` null) | 전체 폐기 | **불변** | 불변 | O | O |
| `base_version` 불일치 | 전체 폐기 | **불변** | 불변 | O | O |
| Pass C fail-open | 영향 없음 | **정상 반영** | 정상 | O | O |
| Pass N/F/E 실패·사용자 중단 | 적용분 폐기 | **불변** | 불변 | **X** | X |
| 프로세스 종료 (완료 커밋 이전) | — | **불변** | 불변 | X | X |
| regenerate | 대상 턴 `before_delta`에서 재계산 | 마지막 활성 형제의 **1회분만** | 그에 따름 | O | O |

### 초안에서 바뀐 칸과 그 이유

초안은 「값 오류」와 「파싱 실패」에도 서버 기본 시간을 적용하자고 했으나 **채택하지 않는다.**

기본값은 **유효하게 파싱된 delta 객체에서 시간 필드만 없을 때**에만 적용한다. 파싱 실패나 stale
patch까지 기본 시간으로 구제하면, A-6의 *"any failure leaves the scene untouched and the beat
continues"* 계약을 조용히 바꾸게 된다. 실패 경로에서 서버가 자기 판단으로 상태를 미는 유일한
예외를 만드는 셈이라, 이번 단계에서는 열지 않는다.

`base_version` 불일치도 같은 이유다 — 불일치는 「이 제안이 어느 세계에 대한 것인지 모른다」는
뜻이고, 세계를 모르는데 시간만 밀 수는 없다. `applySceneDelta`의 기존 `discard` 의미와도 맞는다.

**Pass C fail-open에서 시간을 반영하는 이유**는 유지한다: Pass C 실패는 칩만 잃고 턴은 성공한다는
것이 `beat-post-extras-choices`의 명시적 계약이므로, 턴이 성공했으면 시간도 흐르는 것이 일관된다.

## 5. B-3 혼합 정책의 정확한 의미

```
1. 모델이 advance_minutes 제안
2. 서버가 타입·범위 검증
3. 유효하면 모델 값 사용
4. 누락이면 서버 기본값 사용
5. 턴이 성공 완료될 때만 적용
6. 롤오버는 서버가 day_index에 반영
```

### 누락 · 명시적 `0` · 오류의 구분 (채택)

| 입력 | 의미 | 처리 |
|---|---|---|
| `advance_minutes: 1..1440` | 모델의 유효한 판단 | 검증 후 **모델 값 사용** |
| `advance_minutes: 0` | 「서사적으로 시간이 흐르지 않았다」 | **유효값으로 인정.** 서버 기본값으로 덮어쓰지 않는다 |
| 키 부재 (delta 객체는 유효) | 「모델이 판단하지 않았다」 | **서버 기본값** |
| 타입 오류 / 범위 밖 | 「모델이 형식을 틀렸다」 | 기존 검증 계약대로 해당 키 무시. **기본 시간 적용 안 함** |
| delta 전체 파싱 실패 | 「응답 자체가 깨졌다」 | **시간 불변** |
| `base_version` 불일치 | 「어느 세계에 대한 제안인지 모른다」 | **시간 불변** |

즉 **기본값이 개입하는 경우는 「유효한 delta 객체 + 시간 필드만 누락」 하나뿐이다.**

`0`을 유효값으로 인정하는 근거: 「문을 열자마자 멈춰 서서 쳐다본다」 같은 턴에 강제로 기본값을
밀면 서사가 어긋난다. 다만 **모델이 부재와 `0`을 구분해서 쓸 것이라는 근거는 현재 없다** — 이
구분이 실제로 작동하는지는 §8.2 `clock-advance-observe`가 측정한다.

### 기본값의 균일성

**채택: 첫 구현에서는 모든 턴에 동일한 단일 기본값을 쓴다.** (값 자체는 §6에서 미확정)

`stage`·행동 종류·입력 표현에 따라 기본값을 다르게 하는 휴리스틱은 이 프로젝트에 측정 근거가 전혀
없고, 이 저장소의 선례(`EXTRA_SCORE_ENABLED = false`, τ 사전등록)가 「닿을 수 있는 상수는 조용히
재조정된다」를 이미 경고한다. 균일 기본값으로 시작해 §8.2의 로그를 쌓은 뒤 다시 본다.

## 6. 기본 진행량 — 근거 수준을 구분해서

**결론부터: 현재 자료로는 기본값을 확정할 수 없다.** `+10`은 근거가 되지 못한다.

### 구분해 본 자료

| 구분 | 실측 |
|---|---|
| 모델이 실제 제안한 값 | **관측 2건, 적용 1건.** 2026-09-06 `+10` (적용), 2026-09-02 (미적용) |
| 사용자 문장에 명시된 값 | **파티 대화 사용자 턴 45건 중 2건**(`분/시간/뒤/후/이따/나중` 기준). 나머지 43건은 시간 표현 없음 |
| 서사적으로 타당하다고 사람이 판정한 값 | **자료 없음.** 판정한 사람이 없다 |
| 서버 폴백 후보 | 미정 (아래) |

### `+10`을 기본값 근거로 쓸 수 없는 이유

오늘의 `+10`은 제가 보낸 입력이 **"10분쯤"이라고 숫자를 명시**했고 모델이 그걸 그대로 옮긴 것이다.
모델의 시간 감각이 아니라 전사(轉寫) 능력의 증거이며, 시간 표현이 없는 43/45 턴에 대해서는 아무것도
말해주지 않는다.

게다가 명시해도 안 될 때가 있다 — 2026-09-02의 `"시간도 30분쯤 지났고"`는 **같은 문장의 `weather`만
적용되고 시간은 적용되지 않았다**(§1.2). 즉 명시적 입력에 대한 적용률조차 관측상 1/2다.

### 후보 비교 (근거: 서사 구조 추론, 측정 아님)

| 후보 | 장점 | 단점 |
|---|---|---|
| **1분** | 대사 한 번 주고받기에 가장 가깝다. 24턴이면 24분 — 한 장면이 한 시간 안에 끝난다 | 「서류를 처리하고 다음 절차로」 같은 턴에도 1분이라 누적이 서사보다 느리다 |
| **2–3분** | 대화 턴과 짧은 행동 턴의 중간. 24턴 ≈ 1시간 | 근거가 「중간값이라서」뿐 |
| **5분** | 행동 중심 턴에 자연스럽다 | 대사만 오간 턴에서 과하다. 24턴이면 2시간이라 하루가 빨리 소모된다 |
| **10분** | 오늘 관측된 유일한 값 | **n=1이고 그것도 사용자가 불러준 숫자.** 24턴이면 4시간 — 로비 접수 한 장면에 반나절 |

### 결정: **기본값 미확정**

**`2분`은 제품 기본값으로 확정하지 않는다. 전향 평가용 후보값일 뿐이다.**

현재 증거가 보여주는 것은 이것뿐이다:

- 명시적 10분 입력이 **한 번 적용**됨
- 명시적 30분 입력이 **한 번 누락**됨
- **시간 표현이 없는 일반 턴의 적정 진행량은 관측된 적이 없다**

세 번째가 핵심이다. 기본값이 실제로 쓰이는 곳은 시간 표현이 없는 43/45 턴인데, 그 구간의 관측치가
0건이다. 값을 지금 고르면 근거 없이 고르는 것이다.

값은 §8.2 `clock-advance-observe`의 결과로 `1` / `2` / `3` / `5분` 중에서 확정한다.

## 7. 저장 원자성 위험

**이 위험은 S1/S2 선택과 무관하게 이미 존재하며, 이 ADR이 새로 만드는 것이 아니다.**

한 턴의 최종 커밋은 트랜잭션 없이 3~4개 독립 SQL로 이루어진다:

```
① 블록 행 INSERT/UPDATE (턴 중 여러 번)
② conversations.scene_json UPDATE      (chat.ts:628 / 915 / 1170)
③ scene_state stamp UPDATE             (chat.ts:630 / 917 / 1172)
④ generation_log INSERT
```

②와 ③ 사이에서 프로세스가 죽으면 **conversation scene은 전진했는데 스냅샷이 없는 상태**가 된다.
그 다음 턴은 조상 탐색에서 스냅샷 없는 턴 시작을 만나 conversation scene으로 폴백하므로 — 우연히도
같은 값이라 실질 피해가 없다. ③과 ④ 사이면 로그 한 줄이 빈다.

S2로 옮기면 ②③이 **더 가까워지고 둘 다 성공 경로에만 있으므로 창이 좁아진다.** 다만 없어지지는
않는다.

### 선택지

| | 내용 | 평가 |
|---|---|---|
| **가** | ②③④를 `db.transaction`으로 묶기 | better-sqlite3는 동기라 묶기 쉽다. 다만 생성 경로에 트랜잭션을 도입하는 첫 사례라 SSE·큐와의 상호작용을 확인해야 한다 |
| **나** | scene 저장 실패 시 턴을 `error` 처리 | 이미 화면에 그려진 완성 턴을 사후에 error로 뒤집는 것이라 사용자 경험이 나쁘다 |
| **다** | 재시도 가능한 커밋 단계 | 복잡도 대비 이득이 불명확 |
| **라** | 현재 부분 저장을 수용하고 복구 규칙 정의 | 현행. 위 분석대로 실질 피해가 작다 |

**결정: 「라」(명시적 수용).** 위험을 이 문서에 기록해 두고, 「가」는 필요성이 **관측되면**
`scene-commit-atomicity` 슬라이스로 분리한다(§8.4). 관측된 피해가 없고, 트랜잭션 도입이
`clock-advance`의 전제가 아니기 때문이다.

> **S2 does not make message, snapshot, and conversation scene writes atomic.**
> **It reduces the exposure window but does not remove partial-commit risk.**
> **Atomicity remains a separate evidence-triggered slice.**

S2 채택이 이 위험을 해소한다고 읽혀서는 안 된다. 창이 좁아질 뿐이다.

## 8. 후속 구현 슬라이스 경계

```
1. scene-commit-on-success     ← 먼저 닫혀야 함
2. clock-advance-observe       ← 기본값을 고르기 위한 관측. 적용 없음
3. clock-advance
4. scene-commit-atomicity      ← 필요성이 관측될 경우에만
```

### 8.1 `scene-commit-on-success`

- 범위: 세 경로의 생성 전 `scene_json` 쓰기(`:432`, `:805`, `:1074`) 제거 또는 finish로 이동.
  중단·실패 시 정본 불변 보장.
- 시간 정책 **미포함**. 이 슬라이스만으로는 관찰 가능한 사용자 변화가 거의 없다(§2).
- 금지: 시간 진행, `day_index`, 트랜잭션 도입, 마이그레이션.

### 8.2 `clock-advance-observe`

- 전제: 8.1 완료.
- **제안값을 scene에 적용하지 않는다. 기록만 한다.** 시계는 계속 멈춰 있다.
- 델타 프롬프트 재framing 전/후로 각각 n≥30을 모아 비교한다.
- 분리해서 측정할 항목:

```
advance_minutes 필드 존재율
명시적 0 비율
유효한 양수 분포
잘못된 타입·범위 비율
사용자 입력의 시간 표현 유무
턴의 행동 범주
사람 판정 적정 시간
```

- 산출: `1` / `2` / `3` / `5분` 중 기본값 확정.
- 구현 형태는 `beat_log` 필드 추가이므로 라이브 쓰기 정책을 건드리지 않는다.

### 8.3 `clock-advance`

- 전제: 8.1, 8.2 완료 + 기본값 확정.
- 범위: 델타 프롬프트 재framing 반영, 서버 기본값 폴백(§5 의미론), `day_index` 롤오버(§3.1).
- `ADVANCE_MINUTES_MAX`는 1440 유지이므로 재검토 항목이 아니다.
- 전제 문서: ADR-F9 소유권 표에 `day_index` 행 반영(별도 `PRD`/`ADR` 잠금).

### 8.4 `scene-commit-atomicity`

- 트리거: ②③ 사이 불일치가 실제로 관측될 때. 그 전에는 열지 않는다.

## 9. 테스트 수용 기준 (구현 슬라이스용)

### `scene-commit-on-success`

- 성공 턴: `conversations.scene_json`이 finish 시점에 한 번만 바뀐다
- 중단·실패 턴: `conversations.scene_json`이 **바이트 불변**
- 중단 직후의 다음 턴이 중단 전 상태에서 시작한다 (§1.5 경로가 닫힘)
- 생성 중 `GET /api/conversations`가 이전 확정 상태를 반환한다
- 비트 헤더 블록 내용이 전환 전후로 동일하다 (in-memory 렌더 유지 증명)
- beat·dialog·hunter 세 경로 모두
- 1:1 경로 무영향 (`story_id IS NULL`)
- regenerate 멱등성 회귀 없음 (기존 `sceneBranchSnapshot` 25건 유지)

### `clock-advance`

- 성공 턴마다 `clock_minutes`가 전진한다
- 모델 제안 유효 → 그 값, 누락 → 기본값, `0` → 0, 오류 → 기본값
- `base_version` 불일치 → 시간도 불변
- 중단·실패 턴 → 시간 불변
- Pass C fail-open → 시간 정상 반영
- `1439 → 1440 → 1441` 경계에서 `day_index` +1, `clock_minutes` 정규화
- 역방향·음수·비정수 거부
- regenerate 3회에 시간이 누적되지 않는다 (라이브 `1+3` 절차 재사용)
- 봉인 지연 컷 유지

## 10. 결정된 것과 남은 것

### 이 ADR에서 결정됨

| 항목 | 결정 |
|---|---|
| Scene 정본 의미 | **S2** — 마지막으로 성공 완료된 턴의 커밋된 scene (§2) |
| `day_index` 소유권 | server. 모델 제안 불가. 최소 1, NULL은 1로 해석, 롤오버에서만 증가 (§3) |
| `clock_minutes` 표현 | `0..1439` 정규화. `total % 1440`, `day_index += floor(total/1440)` (§3.1) |
| `ADVANCE_MINUTES_MAX` | 1440 유지. 한 delta당 최대 하루, 다일 진행 불가, 역방향 불가 (§3.1) |
| 누락 / `0` / 오류 | 기본값은 **유효 delta + 시간 필드 누락**에만. `0`은 유효값. 값 오류·파싱 실패·`base_version` 불일치는 전부 시간 불변 (§5) |
| 성공 상태별 반영 | §4 매트릭스 |
| 원자성 | 명시적 수용. 증거가 나오면 별도 슬라이스 (§7) |
| 구현 순서 | `scene-commit-on-success` → `clock-advance-observe` → `clock-advance` → (선택) `scene-commit-atomicity` (§8) |

### 남은 것

1. **기본 진행량의 값.** §8.2 관측 결과로 `1`/`2`/`3`/`5분` 중 확정한다. 그 전에는 확정하지 않는다.
2. **부재와 `0`의 구분이 모델에게서 실제로 나오는지.** §8.2가 「명시적 0 비율」로 측정한다. 나오지
   않으면 `0` 인정 규칙은 사문화되므로 그때 재검토한다.
3. **ADR-F9 소유권 표 수정 잠금을 언제 열지.** 표에 없는 필드는 기본 거부이므로 `day_index`는 코드
   구현보다 ADR 반영이 앞서야 한다. `clock-advance` 착수 전까지 열면 된다.
4. **델타 프롬프트 재framing의 실제 효과.** §1.2의 가설이 맞는지는 §8.2의 전/후 비교로만 확인된다.
   틀렸다면 기본값 폴백이 사실상 유일한 시간 원천이 되므로, 그 경우 정책을 다시 본다.

## 부록 A — 이 문서에서 「사실」과 「가설」의 구분

**실측으로 확인된 사실**

- `advance_minutes`는 `APPLY_KEYS`에 있고 프롬프트에도 있다
- 라이브에서 `clock_minutes`가 저절로 움직인 적이 없다(델타 6회 적용된 대화 포함)
- 2026-09-02 한 문장에서 `weather`는 적용되고 시간은 적용되지 않았다
- 생성 전 쓰기와 finish 쓰기 사이에 `scene_json` 읽기가 없다
- 패스들은 in-memory 값을 받는다
- 클라이언트는 생성 중 700ms로 폴링하지만 `conv.scene`에서 쓰는 것은 `format`과 시트의 문자열뿐이다
- 비트 헤더는 메시지 행에 저장된 서버 렌더 결과다
- 생성 경로에 트랜잭션이 없다
- `day_index`는 ADR 소유권 표에 없고 증가 코드도 없다
- 파티 대화 사용자 턴 45건 중 시간 표현은 2건

**코드 경로 추론 (실행 관측 아님)**

- 중단 턴의 델타가 다음 턴의 폴백으로 계승된다 (§1.5)
- ②③ 사이 프로세스 종료 시 스냅샷 없는 전진 상태가 남는다 (§7)

**가설**

- 시계가 멈춘 원인이 판정기 프레이밍이라는 것 (§1.2). 관측 2건이 지지하지만 재framing 전후 비교로만
  확인된다
- 모델이 부재와 `0`을 구분해서 쓸 것이라는 것 (§5). 근거 없음
- `2분`이 적절한 기본값이라는 것 (§6). 측정 아님
