## 0. 미확정 — 사용자 확정 대기 (Task 1 착수 전 필수)
1. **퍼센타일 컷 α**(§4) — 잠정 "배경분포 상위 5%"(α=0.95) 제안. 이 값 자체가 새로운
   사후선택 여지가 있는 자유도이므로, v1의 θ=0.70처럼 **실행 전 유일값으로 고정**해야
   함 — 이 숫자에 동의하는지, 또는 다른 값(예: 상위 10%)을 원하는지.
2. **판정 합산 규칙 변경**(§5) — v1은 "H1·H2 둘 다 통과해야 채택"(기법 자체의 모델-불문
   강건성 요구)이었으나, v2는 모델별 보정(퍼센타일 기준선·H1 전용 문체완화)을 도입하는
   것 자체가 목적이므로 **"셋 중 하나라도 전부 통과하면 채택 후보"**로 완화 제안(§3 후보
   구성 참조). 이 완화가 v1 정신(사후 규칙 변경 금지)과 충돌하지 않는 이유는 v1은 "이미
  실행한 뒤" 규칙을 바꾸는 것이었고, 이번은 **실행 전에** 미리 다른 규칙을 못박는 것이라
  다름 — 그래도 이 변경 자체를 사용자가 승인해야 함.
3. **보정용 배경 코퍼스 출처**(§7) — lore-v1.json 25건과 별도로, 퍼센타일 기준선을 잴
   "무관 문장" N≥100 코퍼스가 필요(순환논증 방지 — 평가셋으로 컷을 재는 오류 차단).
   `bench/longRp` 또는 `bench/sketchBench` 등 이미 생성된 합성 RP 대화 텍스트를
   재사용(실 라이브 대화 아님, 프라이버시 원칙 유지)할지, 아니면 새로 합성할지 확정 필요.
4. **H1-b(문체완화) 착수 여부**(§3) — 추가 엔지니어링(엔트리 문장분해 또는 대화체
   패러프레이즈 생성)이 필요해 v1보다 범위가 커짐. 이번 라운드에 포함할지, 아니면
   H2-상대컷만 먼저 단독 시도하고 그것도 실패할 때만 H1-b를 여는 순차 게이트로 할지.

## 1. 신호 (Signal)
v1(θ=0.70 절대컷)은 H1(과소발화, 코사인 전구간 저평가)·H2(과대발화, 코사인 전구간
고평가)가 **정반대 방향**으로 실패했다 — REPORT.md 진단: 이건 AND 게이트 로직의 결함이
아니라 **모델별 코사인 스케일 문제**다. v2가 답하려는 질문: 절대 임계값 대신 **모델 자신의
배경분포 대비 상대(퍼센타일) 컷**을 쓰면 이 스케일 문제가 실제로 해소되는가 — 그리고
H1의 저평가는 스케일만의 문제인지, 아니면 entry.content(설명문체) vs RP 대화체 사이의
**문체 격차**까지 겹친 문제인지(H1-b로 분리 검증).

## 2. 대조군 (Control) — 수정 금지
- `loreEntryActive`(`apps/server/src/prompt/loreMatch.ts`), `classify`(`conflict.ts`) —
  v1과 동일, 라이브 코드 무접촉.
- **v1 결과 자체가 역사적 대조군**: θ=0.70 절대컷 비채택 판정은 유지된다. v2가 통과해도
  "v1이 사실 통과였다"가 되는 게 아니라 "다른 방법(상대컷)이 새로 통과했다"가 된다 —
  판정 대상이 다른 기법이므로 소급 적용 없음.

## 3. 후보 (Candidates) — v1과 엔진은 동일, 게이트 방식이 다름
| 후보 | 엔진(재사용, v1과 동일 ONNX·sha256 재확인 후) | 게이트 | 성격 |
|---|---|---|---|
| C1 (H2-relative) | H2 `multilingual-e5-small` | 퍼센타일 상대컷 | H2의 "전구간 고평가"가 스케일 문제라면 상대화로 해소될 것이라는 가설의 직접 검증 |
| C2 (H1-relative) | H1 `paraphrase-multilingual-MiniLM-L12-v2` | 퍼센타일 상대컷 | H1이 저평가라도 "상대적으로는" 진양성이 배경보다 높을 수 있다는 가설 |
| C3 (H1-b-relative) | H1 + entry 문체완화 전처리(§0-4 확정 시) | 퍼센타일 상대컷 | C2가 실패할 경우에만 의미 있는 이차 가설(문체 격차 별도 기여분 분리) |

엔진 재사용 조건: `~/.cache/rpchat-embed/`의 기존 모델 파일 sha256이 v1 REPORT 기록과
일치하는지 Task 0에서 먼저 확인(드리프트 시 재다운로드 후 append로 신규 sha256 기록).

## 4. 성공 기준 (채택 필요조건 — 후보별 개별 판정)
동일 lore-v1.json 25케이스(진양성 10/오발동 3계열 포함 미발동 10/애매 5) **평가셋은
그대로 재사용** — 라벨은 객관적 정답지이므로 재사용이 "결과 재해석"이 아님. 컷 계산에
쓰는 배경분포만 별도 코퍼스(§0-3)에서 새로 만든다.

1. must_fire_recall = 10/10 (v1과 동일 회귀-없음 조건, v1 결함정정 반영)
2. false_trigger(must_not_fire) = 0/10
3. ambiguous top-1 정확 ≥ 50%(≥3/5)
4. **방법론 무결성**(unconditional 게이트): 배경 코퍼스는 평가셋(lore-v1.json)과 완전히
   분리돼야 하고, 퍼센타일 컷 α는 배경 코퍼스 구축 **이전에** 고정(§0-1)돼야 한다.
   이 순서가 깨지면(예: 평가셋 보고 α를 나중에 조정) 결과 전체 무효.
5. 성능 기준은 v1 §4-3 그대로 재사용(idle RSS ≤8GB, 100문장 인코딩 ≤30s) — 참고자료
   아니라 이번엔 채택조건에 포함(관용도 낮춤, v1에서 이미 여유 확인된 항목이라 실질
   문턱은 아님).

## 5. 판정 합산 규칙
- **개별 후보 판정**: C1/C2/C3 각각 §4 전항목 충족이 그 후보의 채택 조건(v1처럼 "전부
  합쳐 판단"하지 않음 — 이유는 §0-2).
- **v2 전체 결론**: C1~C3 중 **하나라도 전부 통과** → 채택 후보(그 특정 엔진+게이트
  조합만 채택 대상, 나머지는 그대로 비채택 기록). **셋 다 불통과** → v2도 비채택,
  P3 계열 종결(추가 v3는 이번 문서가 자동으로 열지 않음 — 또 다른 새 가설+새 사전등록
  필요).
- θ류 사후 조정 금지 계승: α(§0-1) 확정 후 결과 보고 재조정 금지. 순차 게이트(C1 먼저,
  실패 시에만 C2/C3)로 할지 동시 실행할지는 §0-4에서 확정.

## 6. 분기 (Branch)
- 채택 후보 발생(C1~C3 중 하나 이상 전부 통과) → 그 조합만 "채택 후보"로 기록, 실제
  프로덕션 통합(로어 selective 게이트에 임베딩 병행)은 별도 ADR + 다음 슬라이스(본
  벤치 범위 외) — `loreMatch.ts`/`conflict.ts` 수정은 이번 잠금으로 자동 승인되지 않음.
- 전부 불통과 → 비채택, REPORT 작성, 라이브 코드 미변경, B군 "로어 의미 발동"은 v1에
  이어 v2 경로로도 닫힘.
- 엔진 재현 실패(모델 드리프트, 배경 코퍼스 구축 불가) → 벤치 무효 선언, append 정정
  후에만 재시도.
